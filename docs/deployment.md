# Deployment

Production runs on mainnet at [dreptalk.com](https://dreptalk.com) (`www` redirects to the apex). A full preprod mirror runs at [preprod.dreptalk.com](https://preprod.dreptalk.com) for testing governance flows against the preprod testnet. The mirror is a separate worker (`dreptalk-com-preprod`) with its own D1 database and KV namespaces so preprod DReps, governance and logins never mix with mainnet. It also runs its own copy of the gov-sync cron worker (`dreptalk-gov-sync-preprod`) against preprod Koios. Because it sets `CARDANO_NETWORK=preprod`, the middleware tags every response `X-Robots-Tag: noindex, nofollow` so the mirror stays out of search indexes.

The app preprod config is not a `wrangler.toml` environment: the `@astrojs/cloudflare` adapter regenerates the deploy config from the top level only and drops `[env.*]` blocks, so `scripts/preprod-config.mjs` derives it from the adapter's build output instead. The gov-sync worker has no adapter, so it uses a normal `[env.preprod]` block.

Deploys are split per worker and environment so a failed step stays contained and any single target can be re-run on its own: `npm run deploy:app` and `npm run deploy:sync` ship the mainnet app and cron worker, `npm run deploy:app:preprod` and `npm run deploy:sync:preprod` ship their preprod mirrors, `npm run deploy:mainnet` and `npm run deploy:preprod` group the two workers per environment, and `npm run deploy` (alias for `npm run deploy:all`) ships all four. Every mainnet target asks for confirmation before it ships (type `mainnet` at the prompt) so production is never deployed by accident. The preprod scripts run without a prompt. Both environments build from the same source, only `CARDANO_NETWORK`, the bindings and the route differ. Custom domains and their TLS certificates are provisioned automatically from the `dreptalk.com` zone on deploy.

Schema changes are applied per network with `npm run db:migrate:preprod` and `npm run db:migrate:mainnet` (the mainnet one behind the same confirmation prompt as the deploys). `npm run db:migrate:list:preprod` and `npm run db:migrate:list:mainnet` show the applied and pending migrations read-only. Never run the bare `wrangler d1 migrations apply DB --remote`: it defaults to the mainnet database, and the `--env preprod` variant silently falls back to mainnet too because the app `wrangler.toml` has no `[env.preprod]` block. The npm scripts route around that trap, `db:migrate:preprod` resolves the preprod database through the gov-sync `[env.preprod]` config.

Both workers are also deployed automatically: Cloudflare Workers Builds watches the repository and redeploys the app and gov-sync workers on every merge to `main`, so the npm scripts above are for the first deploy, for preprod, and for re-shipping a single target by hand.

The preprod workers need the same config as mainnet, set once after their first deploy. Plain-text values go on the app worker as Worker vars: the legal vars (`LEGAL_*`, documented in `src/lib/legal.ts`), the optional `MODERATORS` allowlist, `TELEGRAM_BOT_USERNAME`, and `VAPID_PUBLIC_KEY` (already in `wrangler.toml`). The CIP-179 survey vars are already in the config files on both networks, nothing to set by hand: `TESSERA_BACKEND_URL` is the feature switch, carried by both workers (gov-sync calls it to mirror surveys, the app reads its presence to serve the category and the answering panel; `src/lib/deployVars.test.ts` holds the two copies equal, since the switch on one side only offers answers on surveys the site can no longer refresh, or mirrors surveys nobody sees), and `TESSERA_APP_URL` on the app worker is the survey card's display-only deep link. Each network points at its own Tessera deployment, and the client refuses a backend whose `/health` reports a different network. Secrets are set per worker with `wrangler secret put`: `KOIOS_API_KEY` on both workers, `VAPID_PRIVATE_KEY` (the pair to the public key, needed for browser push) on both workers, and `TELEGRAM_BOT_TOKEN` plus `TELEGRAM_WEBHOOK_SECRET` on the app worker. Without the push and Telegram secrets the site runs, but those notification channels stay off.

Governance-action submission is preprod-only and needs two more values, both on preprod workers only. `PINATA_JWT` is a secret, the Pinata token for pinning a submitted CIP-108 document to IPFS; without it on the app worker the submit route answers 503 and the rest of the site is unaffected. `PINATA_GOV_GROUP_ID` is a plain var on BOTH workers, the id of a Pinata group created once by hand (`POST /v3/groups/public`). Every upload goes into that group, and the cron worker's `pin-gc` phase refuses to delete any file that is not in it. That matters because the Pinata account is shared with another project: a scoped API key restricts permissions and not which files they reach, so the group, not the key, is what keeps the collector off someone else's data. `PINATA_JWT` goes on BOTH preprod workers, the same value, the way `KOIOS_API_KEY` does: the cron worker's `pin-gc` phase needs it to delete. It is deliberately not a second key. Pinata's Files permission is one None/Read/Write selector and uploading already requires Write, so no token exists that can pin without also being able to delete, and a separate collector key would carry identical rights while adding a second secret to rotate and forget. Leave Groups at None on the key: the collector never touches the Groups API, and without that permission it could not enumerate a group even if someone later tried to make it. The group check before every delete is the actual boundary.

`PINATA_JWT` is also set on the MAINNET workers on purpose, ahead of the feature being enabled there. It does nothing yet: both the submit route and the `pin-gc` phase are off on mainnet, the phase because `PINATA_GOV_GROUP_ID` is deliberately absent from the mainnet vars. Do not remove it as a stray secret. Turning the feature on for mainnet means adding a mainnet Pinata group id, and that group should be its own, separate from the preprod one, so neither network's collector can ever reach the other's pins. Leave any of the three unset and the corresponding half simply does not run: no group or no collector token disables `pin-gc` entirely, which is the safe direction to fail. The same Koios token works on every network (it is tied to the account tier, not the network), so reuse the mainnet token. A free Koios account is enough, but a Pro key is recommended for production: the cron worker's six-hourly DRep enumeration is rate-limit heavy, and the very first sync from an empty database is the heaviest. It is optional but recommended for preprod too:

```sh
npx wrangler secret put KOIOS_API_KEY --name dreptalk-com-preprod
npx wrangler secret put KOIOS_API_KEY --name dreptalk-gov-sync-preprod
```
